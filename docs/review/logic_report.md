## 2. Работа с базой данных (задание 3.2)

### 2.1. Риск SQL-инъекций

**Хорошая новость:** в `base_repository.py` и `client_repository.py` используются только ORM-запросы SQLAlchemy (`db.select`, `db.session.get`, `setattr`) — **сырых SQL-строк с конкатенацией нет**. Риск инъекций в этих файлах отсутствует.

В `database/order_cost_query.sql` — статические SQL-запросы без параметров извне (это скрипт, а не рантайм-запрос), инъекций нет.

⚠️ **Но:** в `app/views/production_order_view.py` (по данным pylint) есть `import sqlalchemy.text` и сырые запросы — нужно отдельно проверить, параметризованы ли они. В текущий срез не вошло, вынеси в отдельное замечание.

| № | Файл | Замечание | Категория | Приоритет |
|---|---|---|---|---|
| 1 | `app/views/production_order_view.py` | Используется `sqlalchemy.text` — нужно убедиться, что все параметры передаются через bind-параметры (`:param`), а не f-строками. | Безопасность | Важно |
| 2 | `database/order_cost_query.sql` | Запросы корректны, но `CREATE OR REPLACE FUNCTION calculate_order_cost(p_sales_order_id UUID)` — функция создаётся в БД, а не в коде. Нет миграции для её создания — при развёртывании на чистой БД функция отсутствует. | БД | Важно |
| 3 | `database/schema.sql` | Схема **не применяется автоматически**: в `app/__init__.py` вызывается `db.create_all()`, который создаёт таблицы по моделям, а не по `schema.sql`. Возможно расхождение (например, `CHECK`-ограничения, индексы, `gen_random_uuid()`). | БД | Критично |
| 4 | `database/schema.sql` | `users.user_id` — `SERIAL`, а все остальные ID — `UUID`. Несогласованность типов первичных ключей. | БД | Рекомендация |
| 5 | `database/schema.sql` | `sales_orders` имеет `CONSTRAINT fk_sales_client CHECK (client_id <> executor_id)` — хорошо. Но нет `ON DELETE` для `client_id`/`executor_id` — при удалении клиента будет ошибка. | БД | Важно |
| 6 | `database/schema.sql` | `notes.id_user` — `INTEGER`, `users.user_id` — `SERIAL` (INTEGER). Согласовано, но в модели `Note` (по тестам) используется `id_user`, а в схеме — `id_user`. Проверить соответствие имени в `models.py`. | БД | Рекомендация |
| 7 | `database/schema.sql` | Тестовые пользователи вставлены с **dummyhash** (`pbkdf2:sha256:260000$admin$dummyhash`) — они не смогут войти. Это нормально для демо, но стоит задокументировать. | Документация | Рекомендация |
| 8 | `database/schema.sql` | Нет `ON DELETE` для `notes.id_user` → при удалении пользователя заметки останутся «висячими» (или удаление упадёт). | БД | Важно |
| 9 | `database/schema.sql` | Дублирование индексов: `idx_product_prices_product` и `uq_product_price UNIQUE (product_id, effective_date)` — уникальный индекс уже покрывает `product_id` как префикс, отдельный `idx_product_prices_product` избыточен. | БД | Рекомендация |

### 2.2. Целостность схемы и ER-диаграмма
